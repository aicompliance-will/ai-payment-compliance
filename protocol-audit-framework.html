协议法律审计 · 八维框架

一个 agentic 支付协议，把哪些法律问题留给了你。

x402、MPP、Visa TAP、Mastercard Agent Pay——大厂在推的 agent 支付标准， 每个都在八个维度上做了选择：明确规定、部分触及、或完全留白。 留白不是没有风险，而是把风险甩给了采用它的人。这套框架逐维拆解， 告诉你协议层留下的洞，以及你要在自己的用户协议里补什么。

agent 执行

框架审计的就是这道接缝——授权从人类交到 agent 手里去执行的那一跳。
协议往往恰恰在此留白，断裂就发生在这里。

01
方法论 / How to read

判断档位测的是「明确度」，不是「风险」

每个维度对协议打三档。但明确度和风险方向相反——这是整套审计最反直觉、也最关键的一点。

明确

协议有清晰、可执行的规定。对应连续 / 合规。

部分

协议触及但未厘清，或只覆盖部分情形。中间态。

空白

协议完全不涉及，留给上层实现者承担。对应断裂 / 风险。

核心逻辑

空白 ≈ 高风险；明确 ≠ 安全

空白判红。协议不置一词，不代表问题消失，而是被甩给实现者——风险最高、最隐蔽。「信息不足 ≠ 无风险」。

明确要读方向。协议可能明确写「不退款、风险自负」——这是明确，但对用户极不利。明确档要继续看它朝哪个方向分配责任。

② ↔ ⑦
共享代理法底层。授权（②，向内对用户）与缔约（⑦，向外对交易对手）同源于 agency law，按视角拆分填写，不重复。
⑥ ↔ ⑧
在数据本地化处有接口。⑥ 看监管管辖叠加，⑧ 看数据主体权利与 controller / processor 定性。

八维详解 / The eight dimensions

从资金进入到数据流出

覆盖一笔 agentic 支付的完整法律生命周期。先速查定位，再逐维拆解。

①资金流向
Fund Flow

资金从付款人到最终收款人的完整路径——经手主体、每段持有时长、结算轨道。

核心问题
  • 是托管（custody）还是过路（pass-through）？资金是否离开用户控制？
  • 是否存在资金池化（commingling）？
  • 结算走什么轨道——卡轨、银行转账、链上稳定币？
  • 持有时点是否产生孳息归属、客户资金隔离问题？
适用提示　custody 判断的事实基础，直接喂给 ⑤。链上协议这一维常「明确」——资金从不离用户钱包——反而是低风险信号。
关联 ⑦
②授权链条
Authorization Chain

从用户意图到最终扣款，每一跳的授权依据是什么。

核心问题
  • 事前授权（pre-auth / mandate）还是事后确认？
  • 授权范围有无金额、时间、对手方上限？
  • 有没有哪一跳是隐含授权，缺明示法律依据？
  • 授权可否撤销？撤销的时点和效力边界？
适用提示　视角向内——钱能不能扣、对用户是否有效。与 ⑦ 共享代理法底层。
③身份与认证
Identity & Authentication

交易中所有需验证的身份及其机制——持卡人 / 用户 / agent 三层身份。

核心问题
  • KYA（Know Your Agent）如何实现？身份对交易对手透传还是遮蔽？
  • 用户能否区分「是我的 agent」与「他人冒名」？
  • 卡轨场景 SCA / 3DS 的 challenge 由谁、如何完成？
  • agent 身份的签发、绑定、吊销机制？
适用提示　卡产品合规（PCI DSS / 3DS / SCA / BIN）归入此维——本质是身份验证标准，仅卡轨协议触发，链上协议此部分为空。
④消费者保护
Consumer Protection

退款权、争议解决、欺诈与错误损失的分配。

核心问题
  • 协议有无内建 chargeback / dispute？没有则用户救济路径是什么？
  • agent 自主决策致损（买错、买贵、重复），损失谁兜底？
  • 错误交易可逆否？回滚由协议层提供还是依赖第三方扩展？
适用提示　卡轨协议继承成熟 chargeback 框架；链上原生协议这一维几乎必然「空白」——off-rail 最大软肋。
⑤牌照义务归属
Licensing Burden Allocation

协议的核心设计，把支付牌照义务（MTL / MSB / EMI / PI）落在谁头上。

核心问题
  • 协议运营方是否因设计本身承担牌照义务？
  • 还是义务被推给上层实现者？还是完全留白？
  • 「我只是协议」的抗辩，在该设计下站得住吗？
适用提示　本维只判断「义务落点」，不列举具体哪张牌照——具体牌照随 ①（custody）、③（卡轨）、⑥（跨境）自然落位。
关联 ⑧
⑥跨境适用性
Cross-border Applicability

协议隐含的司法管辖假设，以及跨境时哪些假设会失效。

核心问题
  • 协议是否默认所有参与方在同一法域？
  • 是否依赖特定国家的授权框架、仲裁条款、数据本地化？
  • 跨境触发的多头监管落在 ①⑤ 的哪些点？
  • 稳定币结算的跨境性质如何定性？
适用提示　多头监管的「叠加」效应在此维统一处理，避免 ⑤ 重复计算同一问题。
关联 ②
⑦缔约与责任归属
Contracting & Liability

agent 代用户缔结合同的法律效力，及违约 / 侵权时的责任落点。

核心问题
  • 代签合同依据是什么——明示授权、默示代理、还是协议自定义规则？
  • 对交易对手是否有效（apparent authority 是否成立）？
  • 出事责任落在用户 / agent 运营方 / 协议运营方哪一方？
  • 协议有无免责或责任转移条款？转移对用户有效吗？
适用提示　视角向外——合同对第三方是否生效、对外责任如何分配。agent 代签合同作为独立风险点在此维落地。
⑧数据与隐私
Data & Privacy

支付数据在协议参与方之间的流转及合规定性。

核心问题
  • 交易数据（金额、对手方、记录）谁是 controller、谁是 processor？
  • 数据是否用于非支付目的（训练、画像）？有无 opt-out？
  • 跨境数据传输是否合规（PIPL / GDPR）？
  • agent 行为数据的归属与留存边界？
适用提示　与 ⑥ 的跨境数据本地化部分有接口：⑥ 看监管管辖，⑧ 看数据主体权利与 controller / processor 定性。

这个全景最该记住的一句

协议不是单选，是叠用

一个真实产品往往同时踩好几个协议——AP2 做授权、ACP 做 checkout、x402 或 MPP 做结算。 所以一家公司的合规暴露，等于它踩的每一层协议空白的 并集（∪）。看完全景，你就知道自己的协议栈在八维上漏在哪。
